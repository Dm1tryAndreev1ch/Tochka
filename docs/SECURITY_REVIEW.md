# Проверка доступа локальной версии

12 октября 2026. Проверены handlers, токены, PostgreSQL business service, CRM outbox, знания, frontend, privacy и launcher. Это проверка кода/регрессий, не внешний penetration test.

## Подтверждённые границы

- app/main.py и app/business.py: UUID недостаточен; проверяются SHA256 токена, срок, ended_at и принадлежность draft. Токен записи — 256-битный HMAC, в БД только хеш; имя/телефон не авторизуют доступ.
- Cookie HttpOnly/SameSite=Strict, Secure в HTTPS-профиле; мутации проверяют Origin, TrustedHost защищает Host. Роли ограничивают конфигурацию, публикацию, audit и удаление.
- app/dialogue.py, app/schemas.py: LLM имеет только ограниченный intent JSON, без SQL/shell/URL-инструментов. Подтверждение контролирует сервер. Произвольный текст frontend выводит через textContent/escaping.
- app/business.py и миграции: ревизия, уникальные ключи, транзакция и EXCLUDE предотвращают устаревшие подтверждения/пересечения. Ценовая версия проверяется при commit.
- app/crm.py: уникальный action id и поиск результата перед повторным POST; разные заявки с одним телефоном не объединяются. Отказ CRM не стирает локальную заявку и не выдаётся за успех CRM.
- app/privacy.py: turns/context/memory/drafts/actions/outbox/contacts очищаются, управление отзывается, обезличивание CRM ставится в очередь. Рабочая retention не удаляет старые backup.
- HTTP body ограничен 128 KB; текст — 2000 символов, WS — 4 KB при штатном launcher, авторизация WS имеет timeout/rate limit и повторную проверку срока.
- Голос: один pipeline, максимум 20 секунд сегмента, две ожидающие STT реплики, 200 реплик на сессию. Модельные запросы имеют timeout. LLM требует server-only API key.
- Аудиозаписи нет, access log выключен. В telemetry не пишутся body, пароли и management tokens; журнал CRM содержит UUID операции, сущность и ошибку.

## Перед публичным выпуском

Локальный профиль использует HTTP/loopback. Нужны TLS, Secure cookie, новые allowed hosts/origins, TURN, пограничные connection limits и реальные сетевые испытания.

EspoCRM требует чтение User для проверки ответственного. Оно read-only, без изменения/экспорта/администрирования; ключ закрыт от браузера/LLM. Для многопользовательского выпуска сузить чтение до команды CRM, добавить индивидуальные учётные записи и actor ID в audit.

Backup содержит персональные данные и секреты; права файлов не заменяют шифрование/политику удаления. Browser traces также приватны. Production-ready статус не заявляется; качество голоса, latency и внешняя приёмка перечислены в IMPLEMENTATION_STATUS.

## Новые поверхности — 13 октября

- Переключение каналов и формы Telegram/SIP закрыты ролями. Оператор не может изменить режим, авторизовать аккаунт или получить SIP-пароли; проверено серверными и браузерными сценариями.
- Регистрация внешнего звонка требует отдельного server-only ключа. TCP AudioSocket принимает только заранее зарегистрированный случайный UUID, с TTL и ограничением соединений/размера пакета. Голосовые действия запрещены до согласия.
- Telegram SDK работает в отдельном процессе; API ID/hash, session SQLite и SIP-конфигурация находятся в приватном каталоге вне iCloud. Общий JSON готовности не раскрывает секреты. Коды входа не записываются в конфигурацию.
- При диагностике служебный ключ канала был выведен CLI; он заменён, связанные службы перезапущены и dialplan перечитан. Старое значение не действует. Не публикуйте CLI-вывод конфигурации/dialplan.
- Подтверждение DTMF работает только в собственной активной сессии и для её текущего черновика. До согласия память/реплики не сохраняются.

Открыто: Telegram-звонок без реального аккаунта не проверен; SIP UDP/RTP в LAN не зашифрован; нет индивидуальных аккаунтов сотрудников, полного supervisor и политики зашифрованных backup новых приватных каталогов. Это не внешний penetration test.
