# Полный план реализации голосовой части

> Исходная программа полной приёмки. Реализованная локальная версия и реально достигнутые результаты — в [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md). Отметки G1–G3 здесь не заменяются автоматическими тестами локальной сборки.

Приоритет P0. План относится к Беларуси и русскому языку, с дополнительным английским профилем. Сначала веб-звонок по ссылке; обычный телефонный номер подключается после проверки SIP. Все этапы ниже запланированы, ни один не отмечен выполненным.

## 1 Результат первой части

Полностью реализованный голосовой продукт принимает обращение, понимает задачу, отвечает по проверенным данным, подтверждает и выполняет допустимое действие, при необходимости передаёт человеку и сохраняет итог в CRM. Должны работать также ошибки, отмены, потеря связи и восстановление.

Четыре проверяемых рубежа:

- **G0 Демонстрация:** один браузерный звонок создаёт подтверждённую заявку в реальной тестовой EspoCRM.
- **G1 Голосовой продукт по ссылке:** русский голос проходит тест естественности, задержек и перебиваний; есть запись клиентов, оператор, администрирование, восстановление и внешний пилот. G1 недостижим для внешних клиентов, пока не решена интернет-доступность.
- **G2 Телефонный адаптер:** всё основное работает на локальных SIP-звонках, включая DTMF и перевод. Публичный номер не нужен.
- **G3 Входящий обычный номер:** есть реальное подключение оператора и проверка звонков с внешних телефонов. Нельзя отметить по одному softphone-тесту.

G1 — законченная первая версия согласованного пользователем канала по ссылке. G2/G3 расширяют её на телефонию. Если работает только G0, всю голосовую часть завершённой не считать. Английский язык имеет отдельную отметку приёмки и не блокирует согласованный русский выпуск.

## 2 Модули и их ответственность

| Модуль | Отвечает за | Не должен делать |
| --- | --- | --- |
| Session gateway | Доступ, лимиты, создание и завершение звонка | Давать браузеру секреты моделей/CRM |
| Transport adapter | WebRTC, позднее SIP/WSS, формат и темп аудио | Решать бизнес-логику |
| Voice runtime | VAD, границы реплик, отмену генерации, playback acknowledgements | Писать напрямую в CRM |
| STT adapter | Аудио, частичные/окончательные транскрипции | Объявлять неустойчивый partial подтверждённым действием |
| Dialogue core | Состояние сценария, знания, язык, вызовы инструментов | Самостоятельно выдавать новые права |
| LLM adapter | Поток токенов и структурированный запрос действия | Выполнять произвольный код из ответа модели |
| TTS adapter | Нормализацию, поток звука, отмену | Озвучивать служебные поля и секреты |
| Action service | Валидацию, подтверждение, транзакции, идемпотентность | Повторять мутацию без проверки исхода |
| CRM adapter | EspoCRM API и сопоставление записей | Требовать платного телефонийного модуля |
| Knowledge service | Версии и опубликованные факты | Индексировать личные данные всех клиентов для общего RAG |
| Operator service | Доступность сотрудников, очередь, передачу разговора | Оставлять бота говорящим одновременно с оператором |
| Audit and jobs | Метрики, события, outbox, повторные попытки | Хранить бессрочно сырые аудиоданные и токены |

Один репозиторий, модульный backend, небольшой frontend и отдельные worker-процессы инференса. Модели подключать через контракт адаптера; конкретная библиотека не должна проникать в бизнес-сценарии. Постоянные модели разделяются между сессиями только с безопасной изоляцией состояния.

Основные события: SessionStarted, SpeechStarted, SpeechStopped, TranscriptPartial, TranscriptFinal, TurnStarted, AudioChunk, PlaybackProgress, GenerationCancelled, ActionRequested, ActionCommitted, HandoffRequested, HandoffCompleted, SessionEnded. Каждый несёт session_id, trace_id, последовательность и timestamp; генеративные события также turn_id и generation_id.

## 3 Этап V00 Проверка оборудования и среды

Оценка 2–3 дня. Зависимостей нет.

Работы:

1. Записать ОС, CPU, RAM, VRAM, свободное место, драйвер NVIDIA, поддержку WSL2/CUDA и реальные интерфейсы сети. На Windows использовать `nvidia-smi`, на Mac — системный отчёт. Доступа ко второму ноутбуку пока нет, результаты не придумывать.
2. Определить режим питания и отключение сна на время тестов, не менять системные настройки без необходимости. Запуск на зарядке, ограниченные фоновые приложения.
3. Создать lock-файлы Python/frontend, конфигурацию без секретов, отдельные окружения несовместимых STT/TTS. Контейнеризировать БД и CRM; Mac Metal-инференс оставить нативным.
4. Составить manifest моделей: точный revision, хеш, размер, runtime, лицензия и источник.
5. Проверить локальную сеть, публичный IPv4/IPv6 или CGNAT. Решить, возможен ли собственный публичный TURN. Отдельно зафиксировать «LAN доступен» и «интернет-звонок доступен».
6. Выбрать тестовую компанию и 10 начальных сценариев. Не выдавать вымышленные услуги за реальные.

Артефакты: паспорт стенда, dependency lock, model manifest, схема сети, конфигурационные профили `mac-local`, `windows-local`, `split-local`.

Приёмка: каждый выбранный runtime запускает один минимальный запрос; лицензии базовой сборки сохранены; опубликован предел памяти; настройка повторяется по инструкции. При неподдерживаемом CUDA сначала использовать CPU-базу, не останавливая весь проект.

## 4 Этап V01 Выбор STT LLM и TTS

Оценка 2–4 дня. После V00.

Поднять небольшой воспроизводимый benchmark runner. Сравнить Whisper small/GigaAM v3/Qwen3-ASR 0.6B; Qwen3-4B-Instruct и Qwen3.5-4B без thinking; Piper/CosyVoice3/Qwen3-TTS 0.6B. Начинать с отдельных компонентов, затем два лучших сочетания под совместной нагрузкой.

Измерять WER, точность ключевых полей, real-time factor, первый chunk, максимальную память, warm/cold старт, устойчивость 30 минут. Для TTS добавить слепое прослушивание живыми русскоязычными слушателями. Подробный протокол — в программе проверки.

Не пытаться установить весь рынок. Для кандидата, который не помещается или требует долгой доработки runtime, записать причину и перейти к следующему. Не превращать выбор модели в бессрочный этап.

Артефакты: CSV/JSON результатов и decision record с выбранным профилем и fallback. Приёмка: есть воспроизводимая контрольная сборка; определён основной кандидат естественного голоса либо честно указан открытый риск. Финальное качество естественного голоса закрывается на V04.

## 5 Этап V02 Первый сквозной браузерный звонок

Оценка 5–7 дней. После V00; V01 уточняет конфигурацию без изменения контрактов.

Реализовать клиент с кнопками начать/завершить, mute, выбором языка, состояниями подключения и разрешением микрофона. Текстовую расшифровку сделать опциональной и доступной для тестирования. Ошибки — «Нет доступа к микрофону», «Помощник занят», «Соединение потеряно», с понятным следующим действием.

На backend: сессия, WebRTC, Pipecat, VAD, STT, локальная LLM, TTS. Начальная цепочка отвечает на 10 FAQ без инструментальных действий. Модели прогреты до ready, процесс не объявляет готовность раньше.

Форматы задаются в адаптерах: для ASR обычно mono 16 kHz; исходный WebRTC и выход TTS могут иметь другие частоты. Ресемплинг делается один раз на границе. Не считать любой байтовый буфер PCM16: проверять sample format, rate и число каналов.

Встроить отмену по завершению сессии и лог времени каждого участка уже сейчас. Установить один активный звонок; второй получает быстрый понятный отказ или форму заявки, а не неограниченное ожидание.

Приёмка: 10 минут разговора и 20 последовательных сессий без роста очереди и потерянных задач; завершение останавливает все потоки; после отказа микрофону интерфейс остаётся рабочим; нет обращений к внешним модельным API. На раннем шаге временная задержка до 2.5 s допустима, но фиксируется.

## 6 Этап V03 Подтверждённая заявка в CRM

Оценка 5–8 дней. После V02. Здесь достигается G0.

Поднять настоящую тестовую EspoCRM с API-пользователем минимальных прав. Реализовать один сквозной сценарий: человек называет услугу и контакт → бот уточняет → читает сводку → получает «да» → сохраняет Lead/Call/Task → подтверждает результат.

Реализовать собственную долговечную запись обращения и outbox. Состояния действия: drafted, awaiting_confirmation, executing, committed, failed, unknown_outcome. Внешняя CRM может временно отставать, но оператор видит pending_sync. Фраза «заявка принята» допустима после собственной подтверждённой записи; фраза «внесена в CRM» — только после успешной синхронизации.

Повтор события и перезапуск worker не создают дубль: ключ действия, таблица сопоставления external ID и проверка результата. Если EspoCRM не обеспечивает нужную серверную идемпотентность, реализовать адаптерную проверку/дополнительное поле и сериализацию записей, а не полагаться на предполагаемый header.

Приёмка: заявка действительно видна в CRM; десятикратный повтор одного события даёт одну логическую заявку; при падении CRM обращение остаётся в локальной БД и синхронизируется после восстановления; клиент не слышит ложного успеха. Демонстрация без CRM-мока.

## 7 Этап V04 Естественный голос и перебивания

Оценка 5–8 дней. После V03.

Добавить выбранный естественный TTS, Smart Turn при подтверждённой пользе, адаптивные паузы и словарь произношения. Номер телефона произносить группами цифр; дату и валюту — в подходящей форме; аббревиатуры и иностранные названия обрабатывать осознанно.

Настроить buffering и передавать короткие законченные речевые фрагменты, не ждать полного длинного ответа. Если выбранный backend возвращает только целый WAV, это отдельное ограничение: заменить backend или ограничить длину фразы и повторно проверить SLO.

Алгоритм перебивания:

1. Во время TTS продолжать принимать входное аудио.
2. Различать вероятную речь, эхо и краткое подтверждение.
3. На новую реплику увеличить generation_id и отменить работу предыдущего ответа.
4. Очистить очередь воспроизведения до фактически слышимого конца, принять playback acknowledgement.
5. Запоздавшие токены и chunks старого поколения отбрасывать.
6. Сохранить в историю только услышанный текст, затем ответить на исправленную реплику.

Неудачная отмена генерации не должна отменять уже подтверждённую запись в расписании. Если пользователь прервал «Вы записаны…» словами «нет, отмените», сначала установить фактический статус действия и провести отдельный сценарий отмены.

Приёмка: целевые задержки и естественность из программы проверки выполнены; 30 сценариев перебивания; ни одного продолжения старого ответа после очистки; нет регулярного самоперебивания эхом. Если проходит только Piper, V04 по естественности остаётся открытым.

## 8 Этап V05 Полноценная запись и знания компании

Оценка 5–8 дней. После V03/V04.

Поддержать: FAQ; услуга и цена; запись; перенос и отмена с проверкой полномочий; сбор сообщения для сотрудника; уточнение непонятного вопроса; отказ при отсутствии фактов. Состояние сценария хранится вне свободного текста LLM.

Сервис записи: рабочие часы, длительность услуги, сотрудник/ресурс, Europe/Minsk, исключения расписания, блокировка/резервирование слота, окончательное подтверждение, идемпотентность. Для пересечений использовать транзакционные ограничения или блокировки, а не только предварительный SELECT.

Слова «в следующую пятницу», «после обеда», «на полчетвёртого» требуют однозначной интерпретации и прочтения конкретной даты/времени. Исправления обновляют draft, а старое подтверждение не относится к новой версии параметров.

Знания: загрузка поддерживаемого текстового формата, проверка, preview, публикация, version_id, архивирование. Файл загрузки — недоверенные данные. Прайс и расписание редактируются структурированно, не выводятся из произвольного PDF в момент звонка.

Приёмка: два клиента пытаются занять один слот — подтверждена максимум одна запись; после изменения времени требуется новое подтверждение; устаревшая цена не выдаётся; не найденный ответ ведёт к уточнению/оператору; пользователь не получает чужую историю по произнесённому номеру. Секретная ссылка управления разрешает действие только для своей записи; истёкший или отозванный токен отклоняется; Caller ID и произнесённое имя без дополнительной проверки не разрешают отмену.

## 9 Этап V06 Telegram и внешний доступ

Оценка 3–5 дней. После V02/V03, финальные испытания после V04/V05.

Создать Telegram-бота с кнопкой звонка, обычной HTTPS-ссылкой и при необходимости Mini App. Для локальных обновлений использовать long polling. Ключ бота хранится серверно; session token короткоживущий; проверяются Origin, срок, роль и лимиты.

Первым внешним каналом остаётся обычный браузер. При ограничениях Telegram WebView показывать «Открыть в браузере». Не имитировать входящий системный звонок Telegram.

Для самостоятельного публичного развёртывания: публичный адрес/узел, DNS и доверенный TLS, coturn, временные credentials, нужные порты и firewall. При отсутствии доступного узла зафиксировать сетевой блокер внешнего выпуска; LAN-разработка продолжается. Тестовый WSS через внешний бесплатный туннель отмечается отдельным профилем с явно иной инфраструктурой и обработкой данных.

Приёмка: iPhone Safari, Android Chrome, desktop browser; дополнительно Telegram Android/iOS, где доступен микрофон. Звонок с мобильного интернета в Беларусь проверен отдельно от Wi-Fi. Проверить строгий NAT, обрыв туннеля/TURN, переход сети, запрет микрофона, блокировку экрана и возврат в приложение. Там, где восстановление невозможно, честно завершить сессию и предложить новый звонок.

## 10 Этап V07 Кабинет и живой оператор

Оценка 4–6 дней. После V03/V05.

Кабинет: список обращений, фильтры, краткое содержание, статус заявки/записи, ошибки синхронизации, очередь на обратный звонок, доступность оператора, редактирование опубликованных знаний. Роли — администратор и оператор. Просмотр чувствительных данных и изменения имеют аудит.

Живой перевод по вебу: принять операторскую сессию, создать управляемый media bridge, соединить клиентское и операторское аудио, остановить генерацию бота. Передать сотруднику краткую сводку и выполненные действия. Для SmallWebRTC мост разрабатывается отдельно; если сложность выше оценки, использовать self-hosted LiveKit как транспорт, сохранив диалоговое ядро.

Порядок владения разговором: bot → handoff_pending → human → ended. После human бот не вмешивается без явного возврата. Если оператор не отвечает в установленное время, бот возвращается к клиенту с фактическим исходом и предлагает заявку на обратный звонок.

Приёмка: клиент и оператор слышат друг друга; бот не говорит поверх сотрудника; timeout не теряет клиента; оператор видит актуальный контекст; отсутствие оператора не маскируется словами «соединяю» бесконечно. Простая созданная Task без живого медиаперевода закрывает только callback, не live handoff.

## 11 Этап V08 Надёжность и ограничения доступа

Оценка 3–5 дней. После V05/V07.

Контроль времени действий, circuit breaker для CRM, ограничение очередей, backpressure, завершение бесконечных циклов инструментов. При смерти модели — короткая заранее подготовленная реплика, fallback или перевод. Если отключён весь узел, браузер сам показывает недоступность; озвучивание мёртвым сервером не предполагается.

Изоляция клиента и организации проходит через все запросы, логи и файлы. Нет произвольного SQL/shell/URL от LLM. Запрещены подстановка tool name и выдача прав текстом документа. Доступ к CRM и моделям закрыт извне, публичен только gateway. Лимит времени сессии и одновременных звонков.

Метрики: active_sessions, rejected_sessions, STT/TTS RTF, time_to_first_meaningful_audio, barge_in_stop_ms, tool_latency, action_errors, CRM_outbox_age, underruns, GPU/RAM peak. Метрики агрегированные, сырые транскрипты не помещать в обычный telemetry export.

Приёмка: выключение каждого процесса даёт предсказуемое состояние; секреты не попадают в frontend/логи; повтор запросов безопасен; prompt injection не даёт чужих записей и новых инструментов; восстановление очереди не удваивает действие.

## 12 Этап V09 Установка восстановление и веб пилот

Оценка 5–8 дней. После V04–V08. Здесь достигается G1, если сеть доступна и проверки пройдены.

Подготовить команды запуска профилей, проверку конфигурации и отдельные liveness/readiness. Установщик до скачивания показывает объём и свободное место. Модели после установки работают из локального кеша. Нет зависимости от пробного API-ключа.

Сделать backup БД, опубликованных знаний, конфигурации и необходимых ключей в защищённом виде. Модели можно восстановить по manifest, а не копировать при каждом backup. Восстановление проверять на отдельной тестовой БД; результат сверять по числу и связям записей.

Проверить часовую нагрузку, затем 8 часов последовательных звонков. Сравнить задержки и память в начале и конце. Это не доказывает промышленную SLA 24/7, но выявляет накопление задач, утечки и нагрев.

Провести ограниченный пилот с добровольными тестировщиками: минимум 50 русских звонков и разбор всех неуспехов. Если английский заявляется пользователю — дополнительно 20 английских. Зафиксировать версии, профиль, известные ограничения и открытые дефекты.

Приёмка: новый разработчик поднимает стенд по инструкции; backup восстановлен; естественность и метрики соответствуют целям; критичных дефектов нет; оператор умеет остановить бота, обработать pending_sync и удалить тестовые данные.

## 13 Этап V10 Asterisk и локальный SIP

Оценка 4–7 дней. После G0 можно готовить адаптер, финальная приёмка после G1. Здесь достигается G2.

Развернуть поддерживаемую ветку Asterisk с chan_websocket, локальные SIP-аккаунты и Linphone. Конфигурацию адресов и медиа брать из версии установленного Asterisk, не копировать случайный dialplan без проверки.

Реализовать входящий звонок, answer/hangup, ARI state, двустороннее аудио, DTMF, busy, no-answer, передачу оператору и возвращение при неуспехе. Отдельно проверить отмену playback/flush при перебивании. DTMF для критичных числовых данных обрабатывается структурированно, не через распознавание тонов LLM.

Поддержать PCMA/PCMU, 8 kHz и согласованный внутренний PCM; широкополосные кодеки вводить отдельно. Проверить одинаковую громкость, pacing, отсутствие ускорения/замедления и одностороннего звука. Caller ID хранится как недоверенное входное поле.

Приёмка: 30 локальных SIP-сценариев, включая DTMF и hangup в середине генерации; перевод реально соединяет звонки; CRM получает одну активность; после завершения нет работающего TTS; SIP-гость не может совершить произвольный платный исходящий вызов.

## 14 Этап V11 Реальная линия компании

Оценка 1–3 дня разработки после предоставления линии. Ожидание договора/настройки оператора не входит в оценку. Здесь достигается G3.

Нужные сведения: оператор, владение номером, доступный SIP-trunk или SIP-регистрация, адреса сигнализации/медиа, разрешённые кодеки, число каналов, входящие тарифы, цена перевода/переадресации, возможность маршрута на сотрудника при недоступности нашей АТС. Не предполагать, что SIP-учётка сотрудника автоматически равна транку.

Сначала тестовый маршрут с ограниченным временем, затем основной входящий. Отдельно проверять внешнюю линию и внутренний звонок; учитывать NAT, timeout регистрации и ограничения адресов оператора.

Fallback при недоступной АТС должен существовать **у оператора или на независимом узле**, иначе выключение ноутбука выключит и резервный маршрут. При отсутствии такого условия явно указать ограничение.

Приёмка: реальные входящие с двух разных внешних сетей, рабочее/нерабочее время, скрытый номер, перевод, завершение со стороны клиента, отключение agent и отключение АТС. Нет непредусмотренных платных исходящих направлений.

## 15 Этап V12 Итоговая приёмка

Проводится в рамках V09/V11; отдельная оценка времени не прибавляется. Проверить полный набор из программы проверки на зафиксированной версии. Выпускать только реально достигнутые рубежи G1/G2/G3 и подтверждённые языки.

Пакет выпуска: исходники, dependency/model manifests, воспроизводимые профили, миграции БД, тесты, примеры конфигурации, инструкция установки, runbook оператора, backup/restore, протокол результатов и список ограничений. Настоящие ключи, клиентские аудио и персональные данные в репозиторий не включаются.

## 16 Минимальные контракты данных

Состояние разговора содержит language, channel, identity_level, current_intent, collected_fields, field_revision, confirmation_revision, action_status, handoff_status и knowledge_version. «Да» подтверждает только последнюю прочитанную пользователю версию параметров. Данные, полученные после этого, требуют нового подтверждения.

Нормализованный результат инструмента имеет status, action_id, correlation_id, safe_user_message и машинные данные. Возможные статусы: succeeded, rejected, needs_confirmation, temporarily_unavailable, unknown_outcome. Ответ модели не может преобразовать unknown_outcome в succeeded.

Например, заявка на запись содержит resource_id, service_id, start_at_utc, timezone, duration_minutes, contact_ref, confirmation_revision и idempotency_key. Клиентское имя не используется вместо внутреннего contact_ref для доступа к персональным записям.

Долговечные сущности: organisations, sessions, turns, actions, bookings, contact_links, knowledge_versions, outbox_events, handoffs и audit_events. Сырые аудио — отдельное необязательное хранилище с доступом и сроком хранения. На старте не нужна отдельная объектная инфраструктура: зашифрованного файлового тома достаточно, если запись вообще включена.

## 17 Риски и заранее выбранные действия

| Сигнал | Действие | Что нельзя утверждать |
| --- | --- | --- |
| VRAM заканчивается | CPU STT, меньший контекст, разделение с Mac | Что размер GGUF равен всей нужной памяти |
| Красивый TTS медленнее реального времени | Другой runtime/модель, разделение нагрузки, fallback | Что первый быстрый chunk доказывает непрерывность речи |
| Частые ошибки номеров/дат | Уточнение, повтор, структурированный ввод/DTMF | Что низкий общий WER гарантирует правильную запись |
| CGNAT и нет relay | LAN-выпуск, отдельное решение внешнего маршрута | Что HTTPS-туннель сам решает WebRTC UDP |
| Отказ CRM | Локальная долговечная заявка и pending_sync | Что CRM уже обновлена |
| Таймаут записи со спорным исходом | Поиск по action_id/idempotency_key | Что можно безопасно повторить любую мутацию |
| Оператор не ответил | Честный возврат к боту и callback | Что перевод успешно завершён |
| Английский хуже русского | Английский не включать в обещания выпуска | Что multilingual означает одинаковое качество |
| Требование собственной SIM | Отдельный ограниченный прототип Bluetooth/SIP bridge | Что обычное приложение гарантированно захватит и внедрит аудио |

## 18 Первые десять рабочих дней

Дни 1–2: паспорт оборудования, лицензии, сеть, базовые окружения. Дни 3–4: контрольные модели и небольшой набор русской речи. Дни 5–7: WebRTC-звонок, метрики, завершение и первый тест перебиваний. Дни 8–10: реальная EspoCRM и подтверждённая заявка, затем первая демонстрация сквозного результата, если совместимость не потребовала дополнительной работы.

Это рабочая последовательность, а не обещание завершённого продукта за десять дней. Следующий приоритет после сквозного результата — естественный голос, точные действия и ошибки, затем публичный пилот и SIP.
